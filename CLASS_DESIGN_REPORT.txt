EE6161 Advanced Programming - Assignment 2
assignment2_final: Class Design Report

1. Design aim

The program uses small, directly named classes and functions to make the
control flow easy to follow. Standard C++ classes, constructors, inheritance,
virtual functions, vectors, unique pointers, loops, if/switch statements and
random-number generation form the game model. Qt Widgets and named slots
provide the interface. No struct declarations or application lambdas are used.

2. Classes and responsibilities

Window inherits QWidget. It creates the setup controls, action buttons,
command input, status labels and event log. Named slots such as
onAttackClicked() call submit("a"). onSendClicked() handles both Send and
Enter. start() reads the setup controls and starts a new game. refresh()
displays current model data. Window performs no combat calculation.

Game owns the player and Board, and tracks position, gold, command count and
whether the game has ended. command() reads and dispatches a command, checks
player defeat and advances time once. Individual actions are deliberately
separated into movePlayer(), pickUpItem(), dropItem() and attackEnemy().
strike() handles one character's attack. advanceTime() updates the command
count and reports phase changes. look() and inventoryText() produce text.

Board owns its width, height and vector<unique_ptr<Square>>. reset() creates
the rectangular board. Each Square is dynamically created with make_unique
and moved into that vector. at() validates both coordinates before using
y * width + x to find the square. New-game population starts with an empty
starting square and exclusive contents in each other square.

Square is a class with two optional unique pointers, one for Item and one for
Character. Game rules permit an enemy, an item or neither, and prevent both
from occupying the square at once. It is intentionally a small data class.

Character is the abstract base class. Its private state contains Race,
accumulated damage and vector<Item> inventory. stats() combines base values,
night-time Orc changes and equipment effects, then subtracts accumulated
damage from health. pick() and drop() enforce carrying and category rules.
weight(), damage(), dead() and read-only accessors provide shared operations.

Human, Elf, Dwarf, Hobbit and Orc each inherit Character. Each overrides the
pure virtual defendedDamage() method. Human and Dwarf return zero; Elf returns
minus one to represent healing; Hobbit returns a random value from zero to
five; Orc returns one quarter of adjusted damage by day and minus one by
night. The five classes match the five races directly, even where two methods
are identical. makeCharacter() is an ordinary helper function with a switch
that constructs the requested concrete class.

Item is a class with constructors and public equipment data: name, category,
weight and attribute modifiers. catalogue() supplies the eight required item
definitions using Item constructor calls. Stats is a class with a constructor
and public attribute fields, used to return a calculation result. Race and
Category are scoped enumerations that avoid unnamed numeric codes.

3. Abstraction and polymorphism

Character::defendedDamage(...) is pure virtual, so Character cannot be
instantiated directly. Game::strike() accepts Character references and calls
the virtual defence method on the defender. The actual Human, Elf, Dwarf,
Hobbit or Orc override is selected at runtime. Both players and enemies use
this hierarchy. Character's virtual destructor permits correct destruction
of derived objects through a unique_ptr<Character>.

4. Ownership and dynamic storage

Window owns one Game by value. Game owns Board by value and the player through
a unique_ptr<Character>. Board owns separately allocated Square objects through
its vector of unique pointers. Each Square owns its optional contents. Resetting
an enemy pointer removes and destroys the defeated enemy automatically.

Character inventory uses vector<Item> by value. It has no fixed count limit;
rings can repeat as long as final carrying capacity permits. Using value
objects is sufficient for these small item records. No shared_ptr, manual
delete, global game state or autonomous enemy AI is needed. Qt parent ownership
manages the child widgets of Window.

5. Operation flow

Startup: main -> Window constructor -> Window::start -> Game::start ->
Board::reset and makeCharacter -> look and refresh -> Qt event loop.

Attack: button clicked -> onAttackClicked -> submit -> command -> attackEnemy ->
strike(player, enemy). If the enemy dies, award its phase-adjusted effective
defence in gold and remove it. Otherwise call strike(enemy, player), even if
the player's strike missed. command then checks player death, calls advanceTime
once and returns text to the interface. submit displays the text and refreshes
status. Failed commands also advance time. Calls after game over do not.

6. Rule decisions and practical limits

The formal race table overrides conflicting examples. Damage is clamped at
zero before applying successful-defence abilities; Orc quarter damage rounds
down. Health at or below zero is defeat. Defence healing has no maximum because
none is specified. Equipment health changes apply immediately; removing a life
ring or adding a strength ring can cause defeat. Dropping a strength ring is
refused if it would leave the remaining inventory overweight.

East accepts e; exit accepts x or the complete word exit, resolving the initial
letter conflict. Empty, failed and unknown commands and cancelled drops count
as commands. Five daytime commands resolve before the phase changes to night.

Board dimensions are selectable from 1 to 100 each as an allocation guard; this
is an implementation limit rather than a fixed board size in the assignment.
Non-start squares independently have 35% enemy, 35% item and 30% empty chances.
Some enemies carry one item. Enemy equipment disappears on defeat, but it
contributes to the defence used for gold. Drops onto enemies or items are
refused. Movement away from enemies is allowed; this also permits escaping
zero-damage or defence-healing stalemates. Exit or defeat ends the game; no
automatic victory is added when enemies are exhausted.

7. Build and verification

assignment2_final.pro opens as a qmake project in Qt Creator. CMakeLists.txt
provides an alternative build and a separate basic_tests console target. Tests
link the same core as the GUI. CMake AUTOMOC and qmake process Q_OBJECT for the
named slots. Only standard C++ and Qt libraries are application dependencies.

Basic test coverage, actual results and platform limitations are documented in
BASIC_TESTS.md and VALIDATION.txt. Windows Qt Creator compilation is required
by the assignment but has not been verified in this macOS environment. No claim
of full Windows platform validation is made.
